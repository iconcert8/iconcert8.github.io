문제

저녁 방송 시간대에 API p95 지연 알림이 유독 많이 왔습니다. 평소 5~30ms면 끝나는 요청이 순간적으로 1초를 넘겼습니다. 에러는 없었습니다. 그냥 가끔, 몰려서 느려졌습니다.

원인

바깥부터 하나씩 지워 나갔습니다.

  • 앱 로직, N+1: 같은 API의 정상 트레이스는 5~30ms
  • 파드: CPU 2~5%, GC 멈춤도 짧음
  • Redis: 느려진 순간에도 1ms
  • 트래픽 급증: 느려진 순간에 요청 수 변화 없음
  • DNS, 커넥션 풀: 에러·대기 0

트레이스를 열어 보니 1.3초 걸린 요청에서 실제 SQL은 38ms였습니다. 나머지는 SQL 직전, 커넥션을 잡는 지점에서 기다리고 있었습니다. 앱 문제인지 DB 문제인지 가르려고 앱을 거치지 않는 모니터링 서버에서 DB를 직접 봤습니다. 거기서도 writer만 느렸습니다. DB 쪽 문제였습니다.

DB 지표를 1초 단위로 보니 느려진 구간마다 같은 쿼리 하나가 있었습니다. 방송 중인 채널 전체를 훑는 풀스캔 쿼리였습니다. 5분 평균 지표에서는 원리적으로 안 보이는 1초짜리 스파이크였습니다. 쿼리 하나가 절대적으로 무거운 게 아니라 DB CPU에 비해 무거웠습니다. 이 쿼리 3~4개가 겹치는 순간 CPU를 넘겨 큐가 쌓이고, 그동안 모든 쿼리가 같이 느려졌습니다.

파다 보니 숨어 있던 문제가 2개 더 있었습니다.

  • 읽기 전용 트랜잭션은 reader로 가야 하는데 전부 writer로 가고 있었습니다. SQL 로깅 라이브러리가 트랜잭션이 읽기 전용 표시를 하기 전에 커넥션을 먼저 잡아서 라우팅이 죽어 있었습니다. 로깅은 꺼져 있어서 얻는 것도 없었습니다.
  • 캐시 인터셉터가 엔티티를 반환하는 메서드는 캐시를 건너뛰고 있었습니다. 인증 필터가 요청마다 DB를 2번씩 다녀왔습니다.

작업

  • read/write 라우팅 복구
  • 채널 전체를 훑는 쿼리를 reader로 이동
  • 죽어 있던 캐시 복구

결과

배포 전후 7일씩 비교했습니다.

  • writer 멈춤(0.5초 초과): 109회 → 3회
  • writer CPU 평균: 25.1% → 15.7%
  • writer 초당 쿼리: 276 → 103
  • API p95 최대: 3.7초 → 2.1초

알림이 줄어든 데는 트래픽이 줄어든 영향도 있어서 "해결"이 아니라 "완화"로 정리했습니다.

이어서 한 것: 슬로우쿼리

정작 슬로우쿼리를 볼 수단이 없었습니다. 그래서 슬로우쿼리를 로그로 모으는 경로부터 만들었습니다. 기준은 실행 시간보다 "결과에 비해 몇 행을 읽었나"로 잡았습니다. 로직으로 풀리면 로직으로, 안 되면 인덱스로.

  • 어드민 VOD 목록: 서브쿼리가 전체를 훑어 임시 결과를 만든 뒤 바깥에서 같은 조인을 또 하고 있었습니다. 쿼리 구조를 바꿔서 데이터가 가장 많은 채널 기준 87~92초 → 0.11초 (개발 서버, 결과 동일 확인)
  • 가동 시간 집계: 읽는 행 85만 → 1.4만
