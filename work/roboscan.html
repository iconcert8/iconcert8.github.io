상황

선배 개발자가 없는 작은 스타트업이었습니다. 실제 공장에 들어가는 품질검증 시스템을 책임 개발자로 맡았습니다. 6축 로봇이 부품 주위를 돌고, 광학 스캐너가 스캔하고, 결과를 서버에 쌓아 모니터링합니다. 모듈은 로봇, 스캐너, 공장 설비, 데이터 서버, 웹 서버 5개였고 언어도 C#, Java, Python, JavaScript로 제각각이었습니다.

대표님과 방향·아키텍처를 회의로 정하고, 개발은 혼자 했습니다. 코드의 약 60%를 직접 짰습니다.

  • RDB·클래스 설계, Spring Boot REST 서버(MariaDB·Elasticsearch), React 모니터링 화면
  • 스캐너용 Python(Flask) 서버, PLC 통신으로 공장 설비 연동, Winform/Unity 조작 화면

모듈 5개를 어떻게 이을까

메시지가 빠지거나 응답이 누락되면 로봇과 스캐너 순서가 어긋납니다. 실제 설비라 오동작하면 비용이 큽니다. 한 번 일어나는 이벤트는 메시지 브로커로, 지금 값이 중요한 상태나 명령은 Redis로 나눴습니다. 그리고 데이터를 주고받을 때 응답 handshaking을 넣었습니다.

  • 브로커 이벤트는 놓치면 끝입니다. 상태·명령은 Redis에 두면 늦게 뜬 프로세스나 재시작한 프로세스도 지금 값을 바로 읽습니다
  • 요청을 보내면 받는 쪽의 완료·실패 응답을 확인한 뒤에 다음 단계로 넘어가게 순차 제어 시퀀스를 짬
  • 모듈마다 스레드로 제어하고, 에러가 나면 스레드가 안전하게 끝나고 화면에 표시되게 함

실제 로봇 테스트

어려웠던 건 높이 2m가 넘는 6축 로봇을 제가 짠 코드로 움직이는 일이었습니다. 에러가 나면 원인이 제 코드인지, 다른 모듈인지, 로봇 쪽인지부터 갈라야 했습니다.

  • 로그 → 다른 모듈 → 제 코드 순으로 확인하고 고치기를 반복
  • 로봇·스캐너·설비 업체와의 소통을 맡았습니다. 말이 엇갈리지 않게 현장 사진, 상황 설명, 용어를 맞춰서 공유하고 해결책을 회의함
  • 공유하고, 회의하고, 일정을 다시 맞추기를 반복하면서 로봇 제어가 점차 안정됐습니다

역기구학

로봇 팔 끝 좌표를 움직이면 6개 축 각도를 계산해 주는 시뮬레이터가 필요했습니다. 로봇 업체는 수식을 주지 않았습니다. 강의 자료와 논문으로 개념부터 공부했고, 막히는 부분은 동료, 대표님과 회의하면서 풀었습니다. 관절별 행렬을 곱하고 자코비안으로 미분하는데 식이 너무 길어서 Python SymPy로 뽑고 Unity C#으로 옮겼습니다. 실제 로봇 대신 시뮬레이터로 티칭할 수 있게 되면서 티칭 시간을 많이 줄였습니다.

  • 수식보다 개념부터 잡음. "축 사이 관계로 행렬을 만들고, 미분해 가며 근삿값을 구한다"까지 이해한 뒤 식은 회의로 풀었음

원인을 못 찾은 버그

Win32 API로 조작 화면 빈 곳에 Unity 시뮬레이터 창을 끼워 넣었는데, 정말 가끔 창 위치가 어긋났습니다. 테스트를 많이 했지만 원인을 찾지 못했습니다.

  • 처음 구조: 시뮬레이터가 상태를 Redis에 쓰면 조작 프로그램이 읽어 화면에 그리고, 조작 프로그램이 명령을 Redis에 쓰면 시뮬레이터가 읽어 실행

원인을 계속 쫓기보다 문제를 일으키는 구조 자체를 없애기로 했습니다. Unity를 웹으로 빌드해서 조작 프로그램의 웹 뷰어에 띄웠습니다. 웹 빌드에서는 Redis를 직접 못 써서 WebSocket ↔ Redis 중계 프로세스를 하나 뒀습니다. 조작 프로그램 쪽 코드는 그대로 두고 깔끔하게 해결했습니다.

  • 조작 프로그램까지 WebSocket으로 바꾸는 안도 있었지만 고칠 범위가 너무 커서 뺌
  • 중계 프로세스는 WebSocket으로 받은 값을 Redis에 쓰고, Redis 값을 일정 간격으로 WebSocket에 보냄. 바뀌는 곳을 서버 쪽 한 곳으로 가둠

결과

  • 실제 공장 생산라인에 품질검증 시스템으로 적용
  • 업체 협업 포함 일정 차질 없이 완료

돌아보면

  • 창 위치 문제는 끝내 원인을 모릅니다. 구조를 바꾼 건 우회지 규명이 아닙니다. 지금이라면 재현 조건과 가설을 기록하며 쫓고, 시간 상한을 정해 전환을 결정하겠습니다
  • 중계 프로세스의 일정 간격 송신은 폴링이라 지연과 불필요한 전송이 있습니다. 값이 바뀔 때만 보내는 쪽이 낫습니다
  • "어느 모듈 문제인가"를 가르는 데 시간이 가장 많이 들었습니다. 지금이라면 모듈별 heartbeat와 한곳에 모은 로그부터 만들겠습니다
