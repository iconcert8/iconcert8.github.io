상황

선배 개발자가 없는 작은 스타트업이었습니다. 실제 공장에 들어가는 품질검증 시스템을 책임 개발자로 맡았습니다. 6축 로봇이 부품 주위를 돌고, 광학 스캐너가 스캔하고, 결과를 서버에 쌓아 모니터링합니다. 모듈은 로봇, 스캐너, 공장 설비, 데이터 서버, 웹 서버 5개였고 언어도 C#, Java, Python, JavaScript로 제각각이었습니다.

모듈 5개를 어떻게 이을까

메시지가 빠지거나 응답이 누락되면 로봇과 스캐너 순서가 어긋납니다. 실제 설비라 오동작하면 비용이 큽니다. 한 번 일어나는 이벤트는 메시지 브로커로, 지금 값이 중요한 상태나 명령은 Redis로 나눴습니다. 그리고 데이터를 주고받을 때 응답 handshaking을 넣었습니다.

역기구학

로봇 팔 끝 좌표를 움직이면 6개 축 각도를 계산해 주는 시뮬레이터가 필요했습니다. 로봇 업체는 수식을 주지 않았고, 저는 기계공학 배경이 없었습니다. 강의 자료와 논문으로 개념부터 공부했고, 막히는 부분은 동료, 대표님과 회의하면서 풀었습니다. 관절별 행렬을 곱하고 자코비안으로 미분하는데 식이 너무 길어서 Python SymPy로 뽑고 Unity C#으로 옮겼습니다. 실제 로봇 대신 시뮬레이터로 티칭할 수 있게 되면서 티칭 시간을 많이 줄였습니다.

원인을 못 찾은 버그

Win32 API로 조작 화면 빈 곳에 Unity 시뮬레이터 창을 끼워 넣었는데, 정말 가끔 창 위치가 어긋났습니다. 테스트를 많이 했지만 원인을 찾지 못했습니다.

원인을 계속 쫓기보다 문제를 일으키는 구조 자체를 없애기로 했습니다. Unity를 웹으로 빌드해서 조작 프로그램의 웹 뷰어에 띄웠습니다. 웹 빌드에서는 Redis를 직접 못 써서 WebSocket ↔ Redis 중계 프로세스를 하나 뒀습니다. 조작 프로그램 쪽 코드는 그대로 두고 깔끔하게 해결했습니다.

결과

  • 실제 공장 생산라인에 품질검증 시스템으로 적용
  • 업체 협업 포함 일정 차질 없이 완료
