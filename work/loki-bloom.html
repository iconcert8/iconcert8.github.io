배경

흩어져 있던 로그 수집 경로를 Alloy → Loki 하나로 정리하고 있었습니다. 로그를 JSON으로 바꾸고 trace_id 하나로 요청 흐름을 따라갈 수 있게 했습니다. 그 과정에서 과거 로그 조회를 빠르게 하려고 Loki의 bloom filter를 켰습니다. 제가 켰습니다.

문제

2주쯤 지나서 며칠 전 알림의 상세 로그 링크를 열었더니 "No data"가 나왔습니다. 대시보드 패널, 상세 로그 추적, trace_id 검색까지 조건이 붙은 과거 조회는 전부 빈 결과가 나올 수 있는 상태였습니다. 로그가 없는 것처럼 보이면 모니터링 자체를 믿을 수 없게 됩니다.

원인

처음엔 데이터 유실을 의심했습니다. 조건 없이 조회해 보니 로그는 그대로 있었습니다. 그런데 라벨 필터를 하나만 붙이면 0줄이 나왔습니다.

instance=~".+"도 0줄, instance=""도 0줄이었습니다. 서로 반대인 두 조건이 둘 다 0줄이면 필터 로직 문제가 아닙니다. 데이터를 아예 안 읽고 있다는 뜻이었습니다. Loki API의 조회 통계를 보니 bloom filter가 "여기엔 없다"고 판단해서 데이터 덩어리(청크)를 다운로드조차 하지 않고 있었습니다. 당일엔 데이터가 메모리에 있어서 보였고, 저장소로 넘어간 뒤부터 안 보였습니다.

공식 문서를 다시 보니 bloom filter는 Experimental 기능이었고, 한 달에 75TB 넘게 쌓는 대규모 환경이 대상이었습니다.

같은 시기 Loki가 메모리 부족으로 재시작되는 것도 있었습니다. 메모리가 튀는 시각이 정확히 8시간 간격이었고, bloom을 만드는 작업의 기본 주기와 같았습니다.

작업

bloom filter를 껐습니다. 데이터는 저장소에 그대로 있어서 끄자마자 기존 알림 링크도 전부 다시 보였습니다. 메모리 부족 재시작도 같이 사라졌습니다.
