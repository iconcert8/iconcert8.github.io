문제

큰 방송이 있던 날이었습니다. 평소보다 훨씬 많은 트래픽이 통계 수집 서버로 들어왔습니다. 그래도 괜찮을 거라 판단했습니다. 방송 전에 서버를 미리 늘려 두었고 k8s HPA도 걸려 있었으니까요.

역시나 HPA가 바로 동작해서 서버가 빠르게 늘어났습니다. 그런데 새로 뜬 서버들이 재시작되기 시작했습니다. 기존에 살아 있던 서버도 재시작했습니다. 죽은 서버의 트래픽이 남은 서버로 몰리고, 그 서버가 또 죽었습니다. 10분도 안 된 사이에 15대까지 증설이 시도됐는데 실제로 요청을 받을 수 있는 서버는 4대뿐이었습니다.

그날 경과

  • 17:31 방송 대비로 최소 서버 수를 2 → 6대로 올림
  • 18시 첫 방송. 동시 접속 34,776명. 버티긴 했지만 CPU 96.8%에 재시작 4회가 이미 있었음
  • 20:00 두 번째 방송. 5분 만에 동시 접속이 16,036 → 53,479명. 같은 6대로 시작
  • 20:04~20:06 첫 재시작. 요청을 받을 수 있는 서버가 4대로 떨어짐
  • 20:09 동시 접속 58,326명으로 정점. 첫 방송보다 68% 많음
  • 20:13~20:14 CPU 100%, 최대 응답 37.4초, HPA 상한 20대 도달
  • 20:19 20대가 모두 요청을 받으면서 재시작이 멈춤. 이 방송에서만 재시작 20회 넘게

원인

k8s 이벤트 로그를 확인했습니다. OOM이 아니었습니다. 파드에 liveness 응답이 없어서 재시작한 거였습니다. 로그 문구는 "연결은 됐는데 응답 헤더를 기다리다 시간 초과"였습니다. 서버는 살아 있었다는 뜻입니다.

처음엔 JVM 웜업을 해야 하나 고민했습니다. 새로 뜬 서버들이 얼마 안 되는 처리량에서 CPU 100%를 치다가 내려갔으니까요. 하지만 이미 떠 있어서 웜업이 된 서버도 결국 CPU 100%를 보이다가 내려갔습니다. 웜업은 본질적인 해결책이 아닌 것 같았습니다.

다시 보니 liveness 체크가 API와 같은 포트, 같은 스레드 풀을 쓰고 있었습니다. CPU가 꽉 차서 요청이 밀리면 liveness 요청도 같이 밀립니다. 서버는 살아 있고 응답이 늦을 뿐인데 k8s는 죽었다고 보고 재시작합니다. 재시작된 서버의 커넥션은 이미 꽉 찬 다른 서버로 몰리고, 그 서버의 liveness가 또 실패합니다.

동시에 닿은 한계 셋

  • CPU: 서버당 2코어 중 1.99코어. 이 위는 없음
  • 파일 디스크립터: 65,535개 중 65,529개. 대부분이 소켓. 응답이 늦어지면서 커넥션이 닫히지 않고 쌓였고, Redis 적재가 Too many open files로 실패
  • HPA: 20대 중 20대. HPA는 제대로 동작했지만 새 서버가 요청을 받기까지 97~164초(중앙값 133초)가 걸렸음

아니었던 것

  • 메모리·GC: 힙 최대 72.5%, GC로 멈춘 시간 비중 최대 2.3%, OOMKill 0건
  • Redis: 동시 연결 최대 196개, 거절 0건. 문제는 Redis가 아니라 앱이 Redis로 갈 소켓을 못 연 것
  • 며칠 전 줄인 서버 사양: 그 전에도 앱이 쓸 수 있는 CPU는 2코어로 같았음

이때 실마리가 되는 문구를 하나 발견했습니다. "파드 liveness 체크는 조심해서 걸어야 한다." 공식 문서에도 부하가 높아서 재시작되는 케이스를 조심하라고 나와 있었습니다. liveness는 데드락처럼 재시작해야만 풀리는 상황을 위한 장치였습니다.

작업

개발 서버에서 같은 상황을 재현했습니다. 다른 조건은 그대로 두고 liveness가 API 포트를 거치지 않게만 바꿔서 같은 부하를 줬습니다. CPU 100%를 쳐도 재시작되지 않았습니다. 요청 97%가 실패하던 게 0%가 됐습니다. 얼마 안 가 HPA까지 동작해서 트래픽도 잘 나눠졌습니다.

재현 실험

  • 처음엔 대조군 없이 기존 설정 그대로 돌렸다가 "재시작 0회"가 나옴. 앱 밖 대기가 약 1.1초라 5초 임계에 안 닿았을 뿐, 아무것도 구별하지 못한 실험이었음
  • 그래서 변수를 하나로 줄임. 이미지·CPU·스레드 수·서버 대수·부하 스크립트는 같게, liveness가 보는 포트만 다르게(A: API 포트, B: 관리 포트). 양쪽 임계를 똑같이 1초·3회로 낮춤
  • k6 1,000 VU로 5분. A는 readiness가 실패하고 8초 뒤 liveness가 같은 문구로 실패. 요청 받을 서버가 0대인 구간이 약 75초
  • B는 느렸지만(평균 1.6초) 실패 0%. readiness가 서버를 잠깐 빼고 다시 넣으면서 버팀

고려한 방법

  • 임계만 늘리기: 이미 120초 유예였음. 포화가 몇 분 이어지면 결국 죽고, 진짜 멈춤 감지만 늦어짐
  • liveness를 관리 포트로 옮기기: 처음 정한 방향. 하지만 같은 JVM이라 파일 디스크립터가 바닥나면 관리 포트도 연결을 못 받음
  • 서버 사양을 4코어로: 비용이 2배고, 재시작이 재시작을 부르는 고리는 그대로 남음. 별도 과제로 분리
  • liveness 제거: 선택. 느려질지언정 죽지는 않게

결국 서버 10개에서 liveness를 빼는 것으로 정리했습니다. 장애 3일 뒤 포트 분리안을 냈고, 다음 날 제거로 한 걸음 더 갔고, 그 이틀 뒤 운영에 반영했습니다.

  • liveness 제거. 설정은 남겨 둬서 다시 붙일 때는 매니페스트만 고치면 되게
  • readiness는 유지. 처리를 못 하는 서버는 트래픽에서 빠져야 하니까요
  • 메트릭 수집용 관리 포트 분리(management.server.port, 앱 포트 + 100). CPU가 꽉 찬 상황에서도 메트릭은 수집돼야 원인을 볼 수 있습니다. 장애 때는 수집이 끊겨 앱 지표가 파일 디스크립터 6,465개에서 멈춰 있었습니다
  • 메트릭 수집 포트 어노테이션도 같이 변경. 빠뜨리면 그 서버 메트릭이 통째로 끊겨서 가장 조심한 부분
  • readiness에서 DB 체크 제거. 공유 의존성을 넣으면 DB가 흔들릴 때 모든 파드가 동시에 빠집니다

liveness를 빼면 서버가 정말 멈췄을 때는 어떻게 하나 고민했습니다. 락을 잡고 안 놓아주거나 I/O 타임아웃이 없어서 행이 걸리는 경우입니다. 이 서버들은 그럴 경로가 거의 없다고 판단했습니다. 혹시 멈추더라도 readiness 체크로 그 서버로는 트래픽이 가지 않습니다. liveness 재시작은 효용보다 잃는 게 더 많다고 판단했습니다.

경우를 나눠 보니 OOM은 커널이 죽이고, 과부하는 readiness가 빼고 다시 넣습니다. liveness만 잡을 수 있는 건 "스레드가 영원히 멈춘 경우" 하나였습니다. 그 하나를 위해 과부하 서버를 죽이는 대가를 치르고 있었고, 그날이 정확히 그 대가였습니다.

결과

  • 재현 실험(개발 서버): 재시작 3회 → 0회, 요청 실패율 97.58% → 0%
  • 요청 받을 서버 최저(개발 서버): 0대(약 75초 전면 중단) → 1대
  • 부하 중에도 메트릭 수집 끊김 0
  • 적용 후 확인(개발 서버): 10개 서버 모두 수집 정상, 90분 동안 메트릭 공백 0, 수집 응답 4~9ms

하나 더

장애 당시 앱 지표만 보면 실패가 거의 없었습니다. 요청이 앱에 닿기도 전에 밀려서 실패했기 때문입니다. ALB 로그로 다시 세어 보니 사용자가 겪은 실패는 앱 로그보다 만 배 넘게 많았습니다. 그 뒤로는 앱 지표만 믿지 않고 사용자 쪽에 가까운 지표부터 봅니다.

  • 앱 로그 실패 186건 vs 사용자가 겪은 실패 약 252만 건(18.40%). 방송 화면 입장 자체를 못 한 경우도 4만 7천 건
  • 그렇다고 데이터가 18% 사라진 건 아님. 요청은 ALB 로그로, 적재는 DB에서 직접 세어 맞춰 보니 실제 유실은 0.95%
  • 유실의 82.6%는 앱에 전달조차 안 된 요청. 앱 안에서 잃은 건 전체의 0.17%로, 전에 넣어 둔 종료 시 큐 비우기(graceful shutdown)가 실전에서 동작함
  • 앱의 요청 카운터로 셌다면 유실을 8.9%로, 실제의 9배로 오진했을 것. 재시작이 잦으면 죽기 직전 수집 못 한 숫자가 그대로 빠짐

남은 것

재시작이 재시작을 부르는 고리는 끊었습니다. 하지만 CPU 한계 자체, 서버가 뜨는 데 걸리는 시간, 방송 전 서버 대수 같은 건 따로 풀어야 할 숙제로 남아 있습니다.

  • 서버당 소켓이 6만 개 넘게 쌓인 이유는 아직 모름. 서버당 동시 접속이 약 7,300명이라 단순 keepalive로는 설명이 안 됨
  • 스레드가 영원히 멈추면 자동 복구 수단이 없음. 요청 받는 서버 비율 70% 미만 알림을 설계까지 했지만, 확률이 낮다고 보고 붙이지 않은 위험으로 남겨 둠

돌아보면

첫 분석은 "그 시각 CPU 데이터가 없다"는 전제로 시작했는데, 실제로는 Prometheus에 15초 단위로 전부 남아 있었습니다. 다시 분석하면서 첫 결론 10건을 고쳤습니다. 18시 방송에서 이미 CPU 96.8%와 재시작 4회라는 신호가 있었는데, 알림이 없어 20시 전에 대응하지 못했습니다. 이제는 데이터가 있는지부터 확인하고, 재현은 처음부터 대조군을 두고 돌립니다.
