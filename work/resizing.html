문제

서버를 EKS Fargate에서 EC2 노드로 옮기는 걸 설계하고 있었습니다. 옮기려면 서비스마다 실제로 얼마나 쓰는지부터 알아야 했습니다. 30일치를 재 보니 CPU 요청량 대비 실사용이 1.3%였습니다. 부하는 방송이 있는 날 하루 두 번만 5~7 vCPU까지 오르고, 주말은 거의 0이었습니다.

Fargate는 파드 요청량 합에 자체 여분을 더한 뒤 정해진 티어(0.25 / 0.5 / 1 / 2 / 4 vCPU)로 올려서 과금합니다. 그러다 어쩌다 실제로 할당된 Fargate 사양을 보게 됐는데, 2 vCPU로 요청한 서버가 4 vCPU 티어로 잡혀 있었습니다. 앱 요청량이 처음부터 2000m이었고, 여기에 Fargate 여분이 더해지면서 2 vCPU 티어를 넘어간 거였습니다. 돈은 4 vCPU를 내고 앱은 절반만 쓰는 상태였습니다. limit을 request와 같게 걸어 둬서 남는 자원은 결제만 하고 쓰지도 못했습니다. 서비스 11종 대부분이 할당된 티어의 CPU를 53~55%만 쓰고 있었습니다.

원인

Prometheus에 PromQL로 직접 물어서 서비스별로 쟀습니다. 재다 보니 그대로 믿으면 안 되는 숫자가 있었습니다.

  • Fargate 노드는 실제 티어와 상관없이 전부 2 vCPU / 3.73GiB로 보고됩니다. 노드 값으로는 계산이 틀려서, 파드 annotation CapacityProvisioned로 실제 과금 티어를 확인했습니다
  • CPU 상위 0.1% 값은 평시 부하가 아니었습니다. 5분 해상도 상위 1%의 8배였고, 들여다보니 파드가 뜬 지 18~132초 구간, 즉 JVM 부팅 순간이었습니다. 이건 따로 걸러 냈습니다
  • 메모리 최대값은 크게 나왔습니다. 힙이 컨테이너 메모리 비율로 잡혀서 예전 큰 컨테이너 기준 값이었습니다. 리사이징 후 24시간 값으로 다시 보정했습니다
  • 로그 수집 사이드카 CPU도 1분 평균(36m)만 보고 50m으로 잡을 뻔했습니다. 부팅을 뺀 순간 피크가 63m이라 100m으로 정했습니다
  • 결국 사이즈를 정하는 건 CPU가 아니라 메모리였습니다

작업

티어 경계에 꽉 채우기

티어 단위로 과금하니 티어 안에서는 다 써도 돈이 더 들지 않습니다. 이미 내는 티어를 앱이 끝까지 쓰게 맞췄습니다.

  • 앱 CPU = 티어 vCPU − 사이드카 100m, 앱 메모리 = 티어 메모리 − 사이드카 160Mi − Fargate 여분 256MB
  • 서비스별 바닥값을 다시 재고 티어 경계에 맞춰 스펙 조정
  • 앱 요청량을 2000m → 1900m으로 낮춰 앱 + 로그 수집 사이드카(100m) + Fargate 여분이 2 vCPU 티어 안에 들어가게 함. 앱 서버 6종은 4 vCPU 8GB → 2 vCPU 4GB
  • CPU limit 제거. limit은 같은 노드의 다른 파드에 영향을 안 주려고 거는 건데 Fargate는 1노드 1파드라 영향을 줄 파드가 없습니다. 남은 효과는 CPU를 굶겨 GC·부팅 지연을 만드는 것뿐이었습니다. 메모리 limit은 유지했습니다

바닥값은 개발 서버에서 직접 밟아 봄

  • 0.25 vCPU 1GB는 메모리 부족으로 죽음, 0.25 vCPU 2GB는 부팅 6분 40초에도 안 끝나 startupProbe에 걸려 죽음
  • 0.5 vCPU 2GB는 부팅 4분 40초로 probe는 통과했지만, 하루 써 보니 부팅·응답이 너무 느려 1 vCPU 2GB로 확정
  • CPU를 내리니 단축 URL 서버가 기동에 실패. 코드에 하드코딩된 DB 커넥션 풀 웜업 타임아웃(5초)을 부팅 경합이 넘긴 거라 30초로 늘림

배포

  • 한 번에 바꾸지 않고 3차에 나눠 배포(08-20, 08-21, 08-25)
  • 통계 수집 서버는 종료할 때 집계를 내보내느라 종료 유예가 길어서 마지막 순서
  • 배포마다 새 파드의 CapacityProvisioned, 재시작·OOMKill, HPA 동작 확인

덤으로, 힙 최대값이 컨테이너 메모리와 똑같이 잡혀 있는 서버를 찾았습니다. 힙이 끝까지 차면 다른 메모리 몫이 없어서 언제든 OOM으로 죽을 수 있는 상태라 같이 고쳤습니다.

고르지 않은 안

  • 사이드카 request를 0으로 해서 합을 맞추기: CPU 경합 때 사이드카 보장분이 사라져서 뺌
  • Fargate에 남고 Savings Plans: 1년 약정이 EC2 이관 계획과 부딪혀서 뺌

결과

  • Fargate 월 비용 $2,343 → $1,327, −43% (추정 단가 기준)
  • 과금 vCPU 50 → 31.5
  • 3차 배포 뒤 재시작·OOMKill 0

산식으로 더 깎을 수는 있었는데(월 $935까지) 바닥값 근처라 얻는 것보다 위험이 컸습니다. 7개 서비스가 부팅·응답 여유를 내줘야 하는 구간이었습니다. 이미 내고 있는 티어를 앱이 다 쓰게 하는 데서 멈췄습니다.

남은 것

  • 단가는 서울 리전 추정치라 실제 청구서와 대조가 남아 있음
  • EC2 이관은 계획 단계. 1파드 = 1노드로 정했고, 인스턴스 계열은 스케일아웃 노드의 버스터블 초과 요금을 따져 본 뒤 정하기로 함

돌아보면

CPU를 내리면 부팅 경로에 하드코딩된 타임아웃이 새 병목이 됩니다. 리사이징할 때마다 기동 경로 타임아웃을 먼저 봅니다.
