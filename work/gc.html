문제

API 서버가 간헐적으로 느려졌습니다. 평소 30~40ms 걸리던 같은 요청이 가끔 1초 넘게 걸렸습니다. GC 그래프를 보니 10분 정도 간격으로 STW가 500ms~1초씩 튀었고 느려진 시점과 겹쳤습니다. 힙도 고정값이라 컨테이너 메모리를 늘려도 힙은 그대로였습니다.

GC를 보기 전까지

  • 처음엔 HTTP 커넥션 풀이나 DB 커넥션 풀 설정을 의심했지만 이상한 점을 못 찾음
  • 남아 있던 트레이스를 보면 매번 다른 지점에서 느려졌음. 특정 코드가 아니라 프로세스 전체가 멈추는 쪽을 의심

원인

Parallel GC를 쓰고 있었습니다. 처리량을 우선하는 GC라 young, old 수집 모두 애플리케이션을 멈추고, 힙이 클수록 오래 멈춥니다. 저희한테 필요한 건 처리량보다 짧게 멈추는 거였습니다.

  • 서버가 2코어라 GC 스레드도 2개뿐. 병렬로 나눠 처리하는 이점이 작았음
  • 메모리 4GB 서버에서 old 영역 수집이 그대로 500ms~1초 멈춤으로 드러남
  • 힙을 고정값으로 잡고 있어서, 메모리를 늘려 버티는 방법도 통하지 않았음

작업

  • Parallel GC → G1GC
  • 힙을 고정값 대신 컨테이너 메모리 비율로 (MaxRAMPercentage)
  • 서버 8개. 한 번에 바꾸지 않고 모니터링하면서 단계적으로 배포

G1GC를 고른 이유

  • G1은 힙을 같은 크기 영역으로 나누고, 멈춤 목표 시간에 맞춰 쓰레기가 많은 영역부터 조금씩 수집함. 멈추는 시간을 예측할 수 있음
  • 비슷한 상황에서 Parallel → G1로 바꿔 평균 500ms → 20ms가 된 외부 사례를 참고
  • 대가로 GC 횟수가 늘고, 동시 마킹에 CPU를, 영역 간 참조 관리에 메모리를 조금 더 씀. 문제는 처리량이 아니라 멈춤이었으니 감수할 만하다고 판단

힙 비율

  • InitialRAMPercentage·MaxRAMPercentage로 지정. 대부분 서버는 70%, 통계 수집 서버는 80%
  • 100%로 두지 않은 건 힙 밖에도 메모리가 필요해서. 메타스페이스, 코드 캐시, 스레드 스택 몫을 남겨야 OOMKill이 안 남

결과

  • STW: 500ms~1초 → 10ms 이하. 하루치 그래프에서 한 번을 빼고 모두 10ms 이하
  • 대신 GC 횟수는 30분당 4회 → 8~9회로 늘었습니다. 한 번에 길게 멈추는 것보다 짧게 자주 멈추는 게 요청 지연에는 훨씬 낫다고 판단했습니다
  • 이후 리사이징 때 JVM 설정을 따로 안 고쳐도 힙이 컨테이너를 따라갔습니다. 컨테이너를 4096 → 3584Mi로 줄이자 힙도 2867 → 2509Mi로 플래그 변경 없이 다시 잡힘

하나 더

나중에 통계 수집 서버가 과부하로 재시작을 반복한 장애 때도 GC는 원인이 아니었습니다. 힙 최대 72.5%, GC로 멈춘 시간 비중 최대 2.3%, OOMKill 0건이었습니다.

돌아보면

멈춤 시간과 GC 횟수는 기록했지만, 처리량이나 CPU, 꼬리 지연이 전환 전후로 어떻게 바뀌었는지는 재 두지 않았습니다. "횟수가 늘어도 괜찮다"를 숫자로 보여 주지 못한 셈입니다. 다음에 GC를 바꾼다면 그 지표들도 같이 남겨 둡니다.
